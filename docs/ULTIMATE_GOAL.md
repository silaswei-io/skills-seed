# Skills Seed 最终目的

## 一句话定义

**Skills Seed 的最终目的，是让 AI Agent 在进入任何已有项目时，能够像熟悉该项目的团队成员一样理解项目规则、边界和能力入口，并据此完成可靠的代码改动。**

它不是生成一份静态项目说明，也不是把整个仓库塞进 Agent 上下文；它把源码学习得到的开发知识与用户维护的 Rule、Workflow 组合成 Agent 可以按任务读取的本地 Skill。

## 希望解决的问题

已有项目中最重要的信息通常并不完整地写在 README 里，而是分散在：

- 代码目录、模块职责和依赖关系中。
- 接口、数据模型和错误处理中。
- Git 演进、已有约定和团队长期规则中。
- 项目背景、术语、兼容性要求和明确禁止事项中。

当 Agent 缺少这些信息时，往往需要反复探索仓库，容易改错模块、绕过既有能力或遗漏契约，甚至将偶然实现误认为项目规则。

Skills Seed 的目的，是把这些信息转化为项目自己的工作上下文，使 Agent 在动手前能知道：

1. 这项需求应该由哪个项目、模块或能力入口负责。
2. 需要先阅读哪些规则、参考资料和源码位置。
3. 哪些内容是团队明确约束，哪些是当前代码支持的可复用实践。
4. 哪些接口、数据、配置、生成产物或跨项目边界可能受影响。

## 最终用户体验

对于使用 Skills Seed 的团队，理想状态是：

- 初始化一次后，项目知识保存在仓库本地，并能随代码持续更新。
- Agent 先读取简洁的入口 Skill，再按任务加载必要的详细 references，而不需要全量加载仓库知识。
- 团队不必每次都向 Agent 解释目录结构、代码规范和领域术语。
- 不同 Agent 可以使用同一份项目知识；分析 Agent 和最终消费 Skill 的 Agent 可以不同。
- 单项目和 workspace 都有清晰边界：子项目保留自己的事实，根工作区负责跨项目路由和影响说明。
- 团队可以审阅、补充、修正和提交这些本地知识，而不是依赖不可见的远程记忆。

最终效果不是让 Agent “自动正确”，而是显著减少无依据探索、重复沟通和错误修改。

## 知识应是什么

Skills Seed 只应沉淀能够帮助未来改动的项目知识，而不是泛化总结或代码摘录。

这些知识包括：

- 项目和模块的职责边界。
- 可复用的能力入口、工具和领域方法。
- 接口、数据、配置、事件、存储和生成产物的约定。
- 错误处理和安全边界。
- 项目特有的业务规则、状态转换和跨模块协作方式。
- 用户明确维护的长期 Rule、术语和 Workflow。

每条知识都应尽可能说明它来自哪里，并明确区分：

| 类型 | 含义 |
|---|---|
| 明确规则 | 团队或用户明确要求遵守的约束 |
| 证据化知识 | 能由当前项目源码、结构或配置支持的可复用实践 |
| 导航性观察 | 帮助 Agent 定位信息的提示，不应被表述为硬规则 |

Agent 的推断、低频样例、通用工程常识和没有项目证据的结论，不应被伪装为项目规则。

## 知识应如何保持有效

项目知识必须跟随项目演进：

- 新代码和新约定出现时，相关知识可以被补充或更新。
- 源码删除、接口变化或实现替换后，失去证据的代码学习结论能够被撤销或降级。
- 用户维护的 Rule 属于明确约束，不应被局部代码变化自动删除或扩展作用范围。
- 生成给 Agent 的 Skill 始终反映当前有效知识，而不是过时的历史总结。

这使知识不是一次性的生成结果，而是项目的一部分：可以学习、更新、审阅、修订和长期维护。

## 最终交付形态

最终交付的是一套模块化、按需加载的项目 Skill：

```text
<project>-dev/
├── SKILL.md
├── agents/
│   └── <target-metadata>
├── references/
│   ├── project-overview.md
│   ├── project-spec.md
│   ├── modules.md
│   ├── business-methods.md
│   ├── rules/
│   │   └── <rule>.md
│   └── patterns/
├── workflows/
│   └── <workflow>.md
└── scripts/
    └── workflows/
```

其中：

- `SKILL.md` 是统一入口，只负责理解任务并路由到必要的项目 reference 或用户 Workflow。
- `references/` 保存源码学习得到的项目画像、能力入口和模式，以及从 `.skills-seed/rules/` 确定性生成的用户规则投影。
- `workflows/` 保存用户维护的测试、部署、验收及其他工作流程；关联脚本位于 `scripts/workflows/`。
- 不同 Agent 的输出格式可以不同，但它们表达的是同一份项目知识。

这套 Skill 应帮助 Agent 在修改前建立正确判断，并在修改中遵守项目实际边界。

用户维护资源以 `.skills-seed` 为单一事实源：Rule 保存于 `.skills-seed/rules/<id>/RULE.md`，Workflow 保存于 `.skills-seed/workflows/<id>/WORKFLOW.md`；生成目录只包含供 Agent 消费的投影，不作为维护或反向学习来源。两类资源都允许有零个或多个；同名输入默认在保留已有内容的基础上增量优化，只有用户显式选择覆盖时才完整替换。

普通项目 Rule 天然属于当前项目。未声明其他范围的工作区 Rule 只属于工作区根；用户可以显式声明受影响的子项目或工作区根路径。AI 可以结构化自然语言，但不得猜测底座代码路径、资源归属或扩大作用范围。只影响一个子项目的 Rule 应归该子项目维护，工作区 Rule 也不自动成为所有子项目的规则。

测试、部署、发布和验收的操作步骤、命令与执行顺序属于用户维护的 Workflow，不从源码推导为项目模式或 reference。源码仍可以提供运行时配置、跨项目依赖和代码契约的影响边界，但不得把这些影响边界改写成工作流程。Workflow 是最终 Skill 的正式组成部分，并由 `SKILL.md` 按用户任务路由。

## 不做什么

Skills Seed 的目的不包括：

- 建设中心化、强制联网的知识平台。
- 替代代码审查、测试、CI、安全审计或项目负责人。
- 把所有历史实现都认定为正确实践。
- 用一份超长文档代替按任务获取的上下文。
- 让 Agent 脱离当前源码和明确规则自行做出权威结论。

## 最终状态

当一个团队能够把 Skills Seed 作为项目的长期知识层使用时，Agent 接到需求后不再先从零猜测“这个项目应该怎么改”，而是能够先理解：

> 项目是什么、规则是什么、改动该落在哪里、哪些现有能力应复用，以及哪些边界不能突破。

这就是 Skills Seed 最终要提供的价值。

## 实现验收原则

为避免“提示词看起来完整、生成结果却不可靠”，实现链路按不同职责分别验收，不使用一个笼统总分替代决策：

- **稳定目标契约**：运行时目标只维护在 `embedfs/templates/prompts/append/knowledge-goal-contract.txt.tmpl`，由提示词加载器注入知识生产阶段；本文只定义产品目标，不作为运行时输入。
- **权威规则同步**：权威文件内容变化必须触发画像刷新；程序根据本次实际输入确定性记录纳入同步的文件和 Markdown 章节，不依赖 AI 回显输入边界，输入收集或记录失败时拒绝用残缺结果替换已有画像。
- **用户资源单一事实源**：Rule 和 Workflow 都先保存在 `.skills-seed`，再由 `generate skills` 投影到最终 Skill；生成产物不可反向成为权威来源。
- **工作流边界**：测试、部署、发布和验收的操作步骤、命令与执行顺序只来自用户维护的 Workflow，不从源码模式推导；Workflow 必须复制到最终 Skill 并由入口路由。权威项目文件中明确写出的命令权限仍作为安全约束保留。
- **焦点分析深度**：焦点的业务/技术属性和风险信号决定 `standard`、`careful` 或 `critical` 分析深度；深度只增加证据核验，不降低知识准入门槛，也不强制增加输出数量。
- **焦点审查边界**：独立知识审查以学习议程中的证据焦点为最小单元，不按固定候选条数机械切批；每个焦点完成后立即保存可恢复状态，全部焦点通过后再做跨焦点全局规范化。审查调用默认串行，不能与源码分析或 workspace 并发隐式叠乘。
- **知识准入**：知识是否持久化继续由证据、适用范围、复用/路由价值和安全边界决定，不与焦点深度混成一个评分。
- **Skill 就绪度**：发布生成结果前确定性检查入口 frontmatter、计划文件、本地链接以及关键权威规则和覆盖记录的投影；失败时不替换现有 Skill。
