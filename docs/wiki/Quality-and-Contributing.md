# 质量与贡献

> **适用场景：** 你要评审生成 Skill 的实际价值、运行质量测试，或参与 Skills Seed 的开发和文档维护。

## 如何判断生成的 Skill 是否有用

最终验收不是模式数量、文件数或提示词长度，而是未来 Agent 能否可靠回答：

1. 这项改动应该落在哪个项目、模块或能力入口？
2. 需要先读取哪些显式规则和参考？
3. 有哪些现有能力可以复用？
4. 哪些接口、数据、配置、生成物或跨项目边界可能受影响？
5. 哪些风险与未知项需要在实施前确认？

这也是 [最终目标](../ULTIMATE_GOAL.md) 对实现和生成结果的共同验收标准。

## 质量检查层次

| 层次 | 关注点 |
|---|---|
| 输入与边界 | 权威来源、候选路径、范围和恢复状态是否正确 |
| 输出契约 | Agent 返回是否满足结构化 Schema 与来源约束 |
| 知识准入 | 结论是否有证据、适用范围和复用价值，是否存在过度推断 |
| 生成交付 | 入口、链接、规则投影、工作流和 references 是否完整可用 |
| 真实任务 | Agent 是否能据此定位、复用、遵守边界并减少错误修改 |

`.test/quality/` 提供可重复的质量评测资源。它必须保持对项目、语言、框架和业务领域无特化假设，评测的是生成 Skill 的通用可用性与契约完整度。

## 开发检查

提交前至少运行：

```bash
go test ./...
go vet ./...
staticcheck ./...
go build ./cmd/skills-seed
```

扩展错误分支、路径边界或持久化行为时，应同时生成统一覆盖率报告，确认新增测试确实进入目标分支：

```bash
go test ./... -coverprofile=coverage.out
go tool cover -func=coverage.out
```

发布迭代遵循仓库的 `.test/release-iterate.sh`，它会更新版本、执行质量门禁、提交、打标签并推送。发布前必须先补充当前版本的中英文更新日志，且不能改写历史版本记录。

## 文档贡献

- 行为入口改变时，更新本 Wiki 相应页面和 README 链接。
- 新增或调整参数时，更新 [命令参考](../COMMANDS.md) 或 [配置参考](../CONFIGURATION.md)。
- 改动学习链路、提示词、领域模型或模板时，对照 [最终目标](../ULTIMATE_GOAL.md) 说明其如何提升未来 Agent 的改动判断。
- 保持中英文页面的信息架构一致；示例应通用，不把测试项目、语言或框架写成产品前提。

详细贡献规则见 [Contributing](../../CONTRIBUTING.md)。
