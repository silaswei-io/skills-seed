# 核心概念

Skills Seed 将不同可信度、不同维护者和不同用途的信息分开保存。正确区分它们，是生成可靠 Skill 的前提。

> **适用场景：** 你需要判断信息应写入 Rule、Workflow、Context，还是应由源码学习和审查。

## 信息类型

| 类型 | 来源与维护者 | 用途 | 不应做什么 |
|---|---|---|---|
| Rule | 用户或团队显式维护 | 定义强制约束、允许范围、命令权限 | 不由源码自动扩展或删除 |
| Workflow | 用户或团队显式维护 | 定义测试、部署、验收等任务步骤 | 不从源码猜测操作顺序 |
| Context | 用户维护的背景、术语与一次性说明 | 补充代码无法表达的意图 | 不替代可验证规则 |
| 项目画像 | 当前结构、模块和关系的观察 | 为 Agent 导航 | 不表述为硬规则 |
| Pattern | 有源码证据的可复用实践 | 帮助复用能力与实现约定 | 不将偶然代码提升为规范 |
| 能力入口 | 经过证据确认的服务、方法或工具 | 帮助避免重复造轮子 | 不脱离声明和调用链解释 |

## 权威优先级

Agent 处理项目改动时，应按以下顺序理解冲突：

1. 用户对当前任务的明确指令。
2. 项目维护的 Rule 与权威项目文件。
3. 用户维护的 Workflow。
4. 当前源码和由它支持的学习结果。
5. 通用工程经验。

当前源码可以证明现有实现，却不能自动授权突破明确规则。例如，一个构建脚本存在，并不表示 Agent 可以自行运行、部署或修改它。

## 证据焦点与模式

学习不会把每个目录名或文件名机械变成业务域。它会为本次候选代码建立证据焦点：每个焦点是一组需要共同阅读才能判断责任、契约、状态、集成或横切边界的最小证据集。

焦点只用于当前取证与审查，不是永久的工作流分类。通过审查的模式才会进入长期知识库；没有证据、适用范围不清或可能误导未来改动的结论应被拒绝或降级。

## 单一事实源与投影

用户维护资源的事实源始终在 `.skills-seed/`：

```text
.skills-seed/
├── context/
├── rules/<id>/RULE.md
├── workflows/<id>/WORKFLOW.md
└── runtime/
```

最终 Skill 中的 `rules/` 与 `workflows/` 是面向 Agent 的确定性投影。不要直接编辑生成目录来维护长期规则，因为下一次 `generate skills` 会重建产物。

## 生命周期

代码学习知识不是永久事实。它会因新增证据而增强，因实现替换而更新，因源文件删除或证据失效而撤销、过期或降级。Rule 和 Workflow 则由用户显式管理，不能被一次源码扫描替代。

理解完概念后，阅读 [学习与同步](Learning-and-Sync.md) 了解它们如何进入最终 Skill。
