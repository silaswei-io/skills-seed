# 学习与同步

## 本地扫描与按需语义补充

默认使用本地 CodeGraph 结构扫描。`learn current` 和 `sync` 使用随发行包内置的 CodeGraph 1.6.2 更新本地结构索引，结构扫描不调用 AI；程序只为重要语义缺口自动调用分析和独立审核，不再进行全仓 AI 议程规划。源码开发构建请先执行 `make bundle`；也可用 `SKILLS_SEED_CODEGRAPH_HOME` 指定官方平台包目录。发行二进制首次使用时解压组件到用户缓存，无需全局 Node/npm，也不在运行时下载组件。

```bash
skills-seed sync
skills-seed codegraph query "HTTP"
# 也可以主动指定需要更深入判断的范围：
skills-seed learn current --semantic --focus internal/order --context "确认取消订单的状态边界"
skills-seed generate skills
```

生成的 `references/code-navigation.md` 按目录链接到符号入口，并要求开发 Agent 先检索、核对签名与调用示例，再决定复用、扩展或新增。目录是结构导航，不是自动推断的业务域。`codegraph callers/callees/impact` 使用查询返回的符号 ID；`codegraph trace <from-id> <to-id>` 查询静态调用路径。动态调用与跨服务关系可能不完整，空结果不能证明没有现成能力。

索引保存到标准 `.codegraph/`，与其他 CodeGraph 工具复用。skills-seed 只增加自己的导航快照和锁文件；扫描范围收缩不会重建共享数据库。源码选择沿用排除规则，缓存与生成 Skill 不参与反向学习。内置索引会按 Go 语言规则校正 SDK 未标注的导出方法，使它们进入能力导航；已被调用且没有独立跨文件行为的方法优先作为调用方证据。未被 SDK 索引的文件会显式列出。解析失败会报错，不冒充扫描成功。

本地扫描会为全部入选文件建立结构导航，并把无需自动语义补充的变更记为 `selection_skipped`，避免下次重复评估；这不是业务知识已提取的声明。只有自动补充完成分析、审核和入库后，才把候选范围记为语义已确认。未完成的候选保持 pending，显式 `--semantic --focus` 可以重新深挖已扫描文件。生成时，源码证据指纹变化的旧 Pattern 暂不投影；原知识仍保留。项目导航由本地索引和已保存知识确定性生成。Rule/Workflow 保持原有维护方式，权威文件应由消费 Skill 的 Agent 按实际路径直接阅读。

工作区默认从显式配置生成项目路由，不通过 AI 猜测跨项目业务关系。子项目按同样策略自动补充；主动深挖时进入子项目使用 `--semantic --focus`。`--context` 只作为本次自动补充的背景；`--focus` 可限制本地扫描范围。`--force` 重新确认当前索引并触发产物刷新。

自动补充优先复核已有业务知识的变更证据，再从 CodeGraph 的真实符号调用边寻找跨文件行为入口、路由和公开能力；普通 import 和接口声明不会单独触发 AI。同文件私有调用实现作为入口证据，不单独构成语义问题。程序沿真实调用边从公开入口或路由覆盖同一调用链的下游候选；下游独立能力、没有可信上游的入口、调用环和旧知识证据仍保留各自的问题。若剩余候选需要多个证据批次，才用紧凑结构事实并行调用 AI 预筛选明确无长期价值的项；筛选失败或不确定时保留候选。只留在本地导航的文件记录为 `selection_skipped`，并非语义已确认；动态调用和孤立实现可通过 `--semantic --focus` 深挖。

候选按证据容量动态组批，输入优先包含完整相关符号、调用路径与已有知识锚点，不再反复发送整文件；普通证据包上限 64 KiB，单文件证据从 192 KiB 的完整输入安全预算中预留提示词空间。旧知识复核优先读取证据锚点。超限或证据不足的候选保留待补充；确定性的容量阻塞按源码指纹缓存，同一输入不会在每次 sync 反复评估，源码或证据策略变化后自动重试，也可显式指定范围重试。预筛选与独立证据批次按 `agent.parallelism` 并行执行；正数为显式额度，`0` 按本机资源自动分配，最多 6 个并行 Agent 调用。分析与独立审查共享同一额度，同一运行状态的检查点、进度与 pending 状态由单一汇聚者更新。正常 sync 会持续处理全部可处理候选，不设置项目级总时长；单次 Agent 调用仍受 `agent.timeout`、重试次数和输入大小保护。单批 AI 失败会保留该批次并继续其他独立批次；`.skills-seed/runtime/local-supplement.json` 分别记录结构覆盖、筛除数量、语义候选、pending 和容量阻塞。增量识别只持久化文件指纹，不保存完整源码快照；源码已删除的旧知识由生成阶段停止投影。

首次学习重点选择路由和跨文件行为入口；增量学习还会评估发生变化的被调用实现，避免遗漏已知调用链中调整过的业务逻辑。

> **适用场景：** 你想更新已生成的 Skills，理解学习阶段，或决定何时只学习、只生成、续跑或重来。

## 选择正确命令

| 目标 | 命令 | 是否生成 Skills |
|---|---|---|
| 日常更新项目知识与产物 | `skills-seed sync` | 是，学习成功且需要刷新时生成 |
| 只学习，不改动生成目录 | `skills-seed learn current` | 否 |
| 已有学习数据，只重新渲染产物 | `skills-seed generate skills` | 是 |
| 预览哪些文件会参与学习 | `skills-seed preview files --mode incremental` | 否 |

完整参数见 [命令参考](../COMMANDS.md)。

选取策略和提示词不针对项目名称、框架或业务目录设特例。项目业务背景与术语写入 `.skills-seed/context/`，本次重点通过 `--context` 提供；它们进入同一补充请求，但不能替代源码证据或用户维护的 Rule/Workflow。业务模式必须经过独立审查后才进入业务地图；目录名不能自动成为业务责任；没有有效画像时，不输出占位概览。

## 当前代码学习链路

默认学习路径的关键阶段如下：

```text
本地 CodeGraph 建立或更新索引
  -> 本地按变更、调用关系和已有知识选择业务语义缺口
  -> 多批候选先用紧凑结构事实筛除明确无长期价值的项
  -> 其余按重要性顺序和证据字节容量动态组批
  -> 仅对本地无法判断的业务语义调用 AI，并独立审查
  -> 知识准入与入库
  -> 确定性生成导航和 Skills
```

本地代码负责路径范围、输入覆盖、结构化契约、来源安全和持久化。Agent 负责基于已给证据判断语义、边界和可复用价值。两者各自承担擅长的部分，避免把业务判断硬编码到本地过滤器中。

单项目 `learn current` 和 `sync` 整轮只展示一遍六个顶层阶段：CodeGraph 索引、本地文件过滤、语义候选规划、结构覆盖提交、逐批语义补充、学习状态保存。动态证据批次的分析、独立审查和入库放在第五阶段的明细中，以已处理候选文件数表示进展；失败批次仍保留待补充状态，其他批次继续。工作区的每个子项目也按此顺序更新状态。等待期间保留动画和耗时显示，只重画变化的行，不反复清空整个进度面板。重定向输出仍使用逐行日志。

## 证据批次与审查

- 每个证据批次由本地选中的问题和相关调用路径组成，不预设业务域名称或产出数量。
- 内部检查点沿用 `EvidenceFocus` 字段标识可恢复的证据组；默认流程不再调用 AI 规划焦点，它也不是最终 Skill 的分类目录。同一批次可以产出多条不同业务责任的模式，由独立审查逐条决定是否入库。
- `EntryPaths` 是该证据组独占的学习责任；`RelatedPaths` 是可共享的只读证据，不抵扣其他输入的学习覆盖。两者都只引用本轮输入文件。
- 默认补充并行处理独立证据批次，直到正常候选全部完成；每个批次的分析结果经过独立审查并保存检查点。公开入口无论是否已有调用方都可成为语义候选，是否保留取决于证据和审查。CodeGraph 负责符号身份、位置、签名和调用事实；AI 补充任务适用性、前置条件与返回语义，审查后还须匹配本轮图中的真实符号。workspace 子项目共享 Agent 并发额度，不设置项目级总时长。
- Claude 与 Codex 的实际运行时 Schema 会按当前批次收紧焦点 ID 枚举与结果数量；增量候选未通过本地证据准入时，若该焦点没有其他合格决策，则保留唯一的 `no_change` 回执，不会把“无可入库模式”误判为“遗漏焦点”。
- Agent CLI 即使返回 success，本地仍执行动态 JSON Schema 与业务 parser 双重校验。结构错误最多进行一次带前次输出和具体校验原因的修复，不重复源码探索；瞬时服务错误按 `agent.retry` 退避。结构修复也受总重试次数限制。`agent.timeout` 是单阶段总预算，包含排队、执行、退避和修复，重试不会重新计时。
- 独立知识审查按完整焦点进行，避免按候选数量机械切分而丢失上下文。
- 本地证据批次确定后立即保存候选和焦点列表；每个焦点在源码分析成功后先保存候选和事实材料，审查成功后再保存审查结果。审查使用独立会话，复用分析时的当前源码路径和结构事实，不继承分析推理。审查失败后的 `--resume` 只补审查；未经审查的候选与移除决策不会进入模式库。失败批次保持待补充，之前成功提交的批次保留。
- `--resume` 复用有效候选与议程，不重新筛选或规划；已记录源码哈希变化、变更超出旧范围或显式重启会使旧状态失效。恢复格式现为 schema 5，不迁移旧检查点；旧格式需使用 `sync --restart`。格式有效时，单独升级 CLI 不会因版本号变化触发重规划。
- 规范化只将存在关联对象的候选交给 Agent；无关联候选原样保留。单一来源模式的 ID、文本和置信度以已审查结果为准，只有真正的多来源合并可以产生新表述。规范化检查点绑定候选、相关既有知识及用户维护的上下文，避免重放过期合并决策。
- 续跑会重新校验已保存的 Pattern 规范化决策。本轮源码候选先以自己的 Pattern ID 重建来源身份，历史 `MergedFrom` 只保留为既有输出谱系，不会回流为当前输入归属；同 ID 当前候选作为该 Pattern 的当前版本覆盖已有记录。重复校验已水合结果时，无歧义谱系只回指其当前有效 Pattern，同一谱系有多个所有者时仍会拒绝。若某条决策确实合并了不同 ID 的能力入口，系统会保留独立候选并覆盖该 checkpoint，不会让错误合并进入模式库或中断入库。
- Pattern 入库与源码基线是分阶段提交的。若中断发生在 Pattern 已入库之后，续跑会恢复已提交的候选发现数、规范化写入数和原始变更范围，`sync` 仍会按上次学习结果判断是否需要生成 Skills。
- 学习摘要区分“发现候选模式”和“规范化写入”：前者是本轮审查后的候选数，后者是包含相关既有 Pattern 在内的最终 upsert 数，因此规范化写入数可能更大。
- 规范化阶段明确丢弃的候选会写入 run journal 与 changelog，并带上 `reason_code` 与简要原因，便于审阅“为什么没入库”。
- workspace `sync` 会在每个子项目的最终进度中区分“有学习变化”“无学习变化并跳过生成”和“无学习变化但补全缺失 Skills”，并在子项目全部完成后汇总变化项目数、文件变化、候选模式、规范化写入和移除数量。工作区关系输入未变化只表示跨项目画像与规范无需重算，不表示子项目没有学习产出。

提高并发不等于减少调用；默认路径优先合并相关证据、复用有效检查点，不按候选条数拆成多个请求。

## 成功与失败边界

存在待评估文件时，sync 会明确报告未完成数量，即使已成功生成阶段性 Skill，也不会显示为全部学习完成。待评估数量不代表已经证实的业务问题数量。

学习成功不代表 Agent 自动证明所有代码都正确。它表示本轮可接受的知识已满足来源、范围、证据和结构校验。生成阶段只消费已保存结果，不重新调用 Agent。

生成阶段还会执行交付 readiness 检查：标准 Markdown 语法中的本地内联链接、引用链接和图片必须指向生成目录中的文件；行内代码、代码围栏、源码索引表达式以及 Go 泛型调用等非 Markdown 链接不会被当作文档链接。若检查失败，优先查看生成目录中的具体文件和归档内容。

遇到 Agent 调用失败、Schema 不兼容或输入覆盖校验失败时，系统不会把半完成结论直接写入模式库。先查看 [学习失败与人工修正](Learning-Failures-and-Manual-Repair.md) 中的 runtime 归档和续跑策略。

## 何时强制重新生成

以下情况通常应执行 `skills-seed generate skills`：

- 新增、更新或删除 Rule / Workflow 后。
- 手动维护 pattern 或 profile 后。
- 切换 Skills 目标或输出路径后。
- 需要验证生成模板变化后的交付内容时。

生成会重建 Skills Seed 管理的输出目录。对产物的手工修改应迁移回 `.skills-seed` 中相应的事实源。
